# 需求与项目文档规则

本规则参考数据中台项目的同名规则，按 Dev Tools 的 Vue / Rust / Tauri / SQLite 技术栈调整。读取、创建、修改、评审或整理相关文档时适用；路径均相对于当前仓库根目录。

## 目录与文件

每个新需求使用以下结构，按实际产物创建子目录，不提前创建空目录：

```text
docs/产品文档/{需求}/
├── MOC.md
├── prd/
├── design/
│   ├── lld/
│   └── fld/
├── deploy/
│   └── sql/
├── testcase/
└── incoming/
```

| 文档类型 | 位置 | 内容 |
| --- | --- | --- |
| PRD | `prd/PRD-{需求名称}.md` | 问题、目标、需求、业务规则、验收标准 |
| LLD | `design/lld/LLD-{需求名称}.md` | Rust、IPC、HTTP、CLI、SQLite 设计 |
| FLD | `design/fld/FLD-{需求名称}.md` | 页面、组件、状态、交互与接口消费 |
| 发布文档 | `deploy/` | 构建、安装、数据升级、验证与回退 |
| SQL 资产 | `deploy/sql/` | 本需求实际需要的 SQLite 升级或核查脚本 |
| 测试用例 | `testcase/testcase-{场景}-{YYYY-MM-DD}.md` | 前置条件、步骤、预期和验收覆盖 |
| 原始资料 | `incoming/` | 用户原始输入、会议纪要、导出资料 |
| 需求索引 | `MOC.md` | 实际存在的文档、关联代码、规格和变更记录 |

- 需求目录使用可检索的中文业务名称；现有需求已有目录时沿用。
- 正式 PRD、设计、测试与发布说明默认使用 Markdown。用户明确指定其他格式时遵循用户要求，必要时补充 Markdown 索引。
- 链接目标相对当前文档解析；代码定位使用仓库相对路径。不得写本机绝对路径、其他项目工作区路径或失效占位链接。
- `incoming/` 为事实来源，未经用户要求不覆盖、改写或删除原始资料。
- `MOC.md` 仅登记实际生成的文件；新增或修改产物时增量更新链接、状态及变更日志。
- 现有 `docs/*-对接文档.md`、CLI 安装说明和 Git 操作说明保留原位置，持续维护；通过需求 MOC 关联，不复制出另一套契约。
- `docs/README.md` 是项目文档入口；新增需求时追加 MOC 入口。多业务线确有需要时才增加 `PROFILE.md`，不虚构业务线或负责人。
- OpenSpec 产物仍写入 `openspec/changes/` 和对应规格目录，需求 MOC 链接这些产物，不将其搬进产品文档目录或复制正文。

## 编写与核实

1. 先读用户输入、当前需求原始资料、已有 PRD、相关设计及规格。
2. 涉及当前行为、接口、数据模型或可实施性时，在 `src/`、`src-tauri/` 核实；不能用旧文档替代代码事实，也不能因维护文档顺带改业务代码。
3. 区分“已实现”“拟新增”“假设”“待确认”；设计未来行为时允许提出新契约，但标为提案，不能写成现有接口。
4. 缺失信息标为 `[待确认：TC-01]`，说明影响及确认来源；仅在阻止当前工作时向用户澄清，不因模板字段缺失重复索要已知信息。
5. 文档与代码冲突时记录具体路径与差异；现有行为按代码核实，目标行为按已确认需求表达，避免静默改变需求。
6. 修改已有文档保留有效内容，更新日期、版本、状态及变更记录，不为统一措辞重写无关章节。

## 设计文档分流

技能位于 `.agents/skills/`，与仓库已有 OpenSpec 技能保持同一发现路径。

- PRD：使用 `prd-writer`，输出当前需求的 `prd/`。
- 涉及 `src/` 页面、路由、组件、样式、前端状态或 IPC 消费的设计文档：使用 `fld-generator`，输出 `design/fld/`。
- 涉及 Rust 模块、command、HTTP、CLI、数据库、事务、托盘或后台任务的设计文档：使用 `lld-generator`，输出 `design/lld/`。
- 全栈设计分别写 LLD 与 FLD，各自说明职责，通过同一契约链接关联，不重复维护完整字段表。
- 涉及 SQLite 结构 / 数据变更、Tauri capability、插件权限、端口 / 配置、安装包、PATH、发布顺序或回退时：使用 `deployment-doc-generator`，输出 `deploy/`，SQL 按需放 `deploy/sql/`。
- LLD 将已核实的表、接口、权限和文件清单交接给发布文档；发布方案确定后回填版本、脚本、执行顺序与待确认项。
- 对外接口变化使用 `api-sync` 更新现有对接文档，分别核对 IPC、HTTP、CLI；契约表不凭单个入口推断其他入口。
- 使用 `ai-test-case-generation` 从 PRD 功能编号和验收标准派生测试用例，并更新 MOC。
- 简单文档修订和小修复按影响范围交付，无需强制生成 PRD、双端设计和发布文档全套。
- 编写命令、SQL、发布说明不等于已执行；实际操作遵循用户对目标与影响范围的授权，不对已授权步骤重复索要确认。

## PRD 内容

按复杂度组织，不保留空模板章节；至少覆盖背景、目标、范围与可执行验收标准。

1. 文档信息：版本、日期、状态、参考来源及变更记录。
2. 背景与问题：开发者使用场景、痛点及建设原因。
3. 目标与成功标准：可观察、可判定的结果。
4. 范围：本期功能、后续阶段与外部依赖。
5. 用户与场景：桌面使用者、扩展调用方、脚本调用方，按实际需求列举。
6. 业务流程与规则：对象状态、输入校验、时间单位、唯一性、重复操作及数据删除语义。
7. 功能需求：稳定编号如 `FR-01`，描述入口、前置条件、操作、结果及失败反馈。
8. 数据与接口影响：业务字段语义、现有兼容性和上下游关系；技术实现放设计文档。
9. 异常与边界：空数据、非法输入、并发、端口占用、剪贴板不可用、数据损坏、外部失败等适用场景。
10. 验收标准：编号如 `AC-01`，覆盖适用的正常、异常与兼容场景。
11. 待确认与依赖：确认来源、已知负责人及对范围的影响；未知负责人不虚构。

## cURL 示例规范

项目接口文档中的 Linux cURL 示例默认以 **cURL 7.29 + sh / bash** 为兼容目标；用户明确其他版本时按其要求调整。

- JSON 正文使用 `-d` 或 `--data-binary`，显式添加 `Content-Type: application/json`。需要保留原始正文 / 文件字节时优先 `--data-binary`。
- 不直接使用 `--json`、`--data-raw` 等较新选项；将 `--json` 转换时还需保留其 `Accept: application/json` 语义，已有自定义头优先。
- 使用纯 URL，不把 `[地址](地址)` 的 Markdown 链接粘进命令。Shell 参数使用 POSIX 单引号；正文中的单引号用 `'\''` 拼接，不能在普通单引号内用 `\'` 代替。
- 多行续行的反斜杠必须紧接换行，不能在其后追加空格或说明。操作说明单独成段，不附在命令末尾。
- JSON、SQL、`${...}` 业务模板占位符和大整数 ID 保持原文；不通过 JSON 重新序列化“格式化”正文。区分 Shell 变量与需原样发送的业务模板。
- `--data-raw '@文字'` 是字面正文，不能直接改成读取文件的 `-d '@文字'`。`-d @文件` 与 `--data-binary @文件` 对换行的处理也不同，不相互盲目替换。
- 未知参数与较新网络 / TLS 选项需核实兼容性，不能悄悄删除或宣称已在目标服务器验证。记录实际验证环境。
- 可以用“cURL格式化”菜单生成兼容命令；文档只用虚构凭据，命令生成与真实请求执行分别记录。

```bash
curl --url 'https://example.com/api/query' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  --data-binary '{"sql":"SELECT * FROM orders WHERE status = '\''ready'\''","limit":10}'
```

## 文档元数据与状态

新 PRD、LLD、FLD、发布说明和测试用例使用以下 frontmatter；既有对接文档无需批量补齐。日期用实际创建或修改日期，代码路径只登记真实存在的文件；拟新增文件在设计正文另列。

```yaml
---
title: 域名管理需求
status: in_progress
business: dev-tools
module: cookie-bridge
requirement: 域名管理
created: 2026-11-03
updated: 2026-11-03
author: AI 辅助编写
related-code:
  - repo: tauri-app
    path: src-tauri/src/cookie_bridge/
  - repo: tauri-app
    path: src/views/CookieBridge.vue
---
```

| 状态 | 含义 |
| --- | --- |
| `in_progress` | 草稿、编写中或仍有影响结论的待确认项 |
| `completed` | 文档达到当前交付范围，关键事实和引用已核实 |

- `completed` 表示文档完成，不表示代码实现、测试执行、用户验收或发布完成。分别记录这些结果。
- 本项目尚未配置由文档状态触发的 Obsidian 同步，不声明“标为完成即可自动同步”，也不擅自向外部写入。
- 测试文档区分“未执行 / 通过 / 失败 / 阻塞”，不能将预期结果填成实测结果。

## 质量与边界

- PRD 表达业务目标和验收；LLD / FLD 表达方案；实现回顾描述实际代码。发现目标不可实施时反馈需求约束。
- 设计覆盖架构、接口定义与数据模型；适用时说明线程、锁、事务和升级路径。没有持久化影响时明确说明，不编造表结构。
- 契约文档列清字段名、类型、必填 / 可空、单位、错误及兼容性。尤其核对 `/push` 的历史格式、JSON 的 camelCase 与查询参数的 snake_case 差异。
- 页面需求覆盖加载、空、错误、成功反馈与重复操作；桌面能力说明在浏览器预览和真实 Tauri 中的可用性。
- SQLite 设计核实外键、WAL、事务及已有数据升级；区分任务分支软删除与域名级联删除。
- 发布说明区分 macOS / Windows、GUI / console 二进制；记录实际测试平台，未测平台明确标记。
- 示例使用虚构域名、Cookie 与 token；不把真实登录态、剪贴板、用户数据库或日志当文档附件。
- 不迁入参考项目的 Java、MySQL、菜单权限、租户、多语言框架等未在本项目实现的约束。
